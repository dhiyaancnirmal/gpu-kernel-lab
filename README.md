# GPU kernel lab

Matrix multiply and softmax written from scratch in CUDA C++, one optimization at a time, each stage checked against PyTorch and timed against cuBLAS and `torch.softmax` on the same GPU. A roofline chart shows how close each stage gets to the hardware's memory and compute limits.

- **Matmul (fp32), 6 stages:** naive, coalesced, shared-memory tiles, 2D register blocking, vectorized `float4` loads, TF32 tensor cores (WMMA).
- **Softmax (fp32, row-wise), 3 stages:** thread per row, block per row with warp shuffles, single-pass online softmax with `float4` loads.
- **Fused attention forward (Triton, fp16):** FlashAttention-2 style, compared with PyTorch's FlashAttention backend and with naive attention that materializes the N x N scores.
- **Measurement:** CUDA events, warm-up, median of repeated runs, L2 flushed before each run, a float64 reference for correctness, and a copy kernel to measure the real DRAM bandwidth ceiling.

## Reproduce

Everything except the GPU tests runs on a machine without a GPU (the Triton kernel runs in Triton's CPU interpreter).

```sh
uv venv && uv pip install -r requirements-ci.txt   # CPU torch and pip's CUDA toolkit
python -m pytest                                   # compile check, CPU tests, README check
```

On a GPU, through [Modal](https://modal.com) (one A10, about 10 minutes for the full run):

```sh
pip install modal && modal setup
modal run modal_app.py --quick          # smoke run on small sizes
modal run modal_app.py                  # build, run the GPU tests, benchmark, write results/a10.json
python -m gkl.report results/a10.json   # regenerate README tables and the roofline chart
```

On a local NVIDIA GPU: `make && python -m pytest && python -m gkl.run --out results/local.json`.

## How it works

All kernels compute `C = A @ B` for row-major fp32 matrices of any shape (no multiple-of-tile assumption: edge tiles are zero-filled on load and masked on store). Python calls them through a small C ABI ([`csrc/gkl.h`](csrc/gkl.h)) with `ctypes`, passing torch tensor pointers and the current CUDA stream.

### Matmul ([`csrc/matmul.cu`](csrc/matmul.cu))

A square fp32 matmul of size n does 2n^3 FLOPs on 12n^2 bytes of input and output, so at n = 4096 it needs about 680 FLOPs per byte of compulsory traffic: far above any GPU's ridge point. A good kernel is compute-bound; every stage below removes a reason it is not.

0. **Naive.** One thread per output element, with `threadIdx.x` mapped to rows. Adjacent threads in a warp read A rows K floats apart and write C elements N floats apart, so each warp-wide access becomes 32 separate memory transactions.
1. **Coalesced.** Swap the mapping so `threadIdx.x` walks columns. Now a warp reads one A value (a broadcast) and 32 consecutive B values per step: one transaction instead of 32. Same arithmetic, same code, much less DRAM traffic.
2. **Shared-memory tiles.** A 32x32 thread block copies a 32x32 tile of A and of B into shared memory, synchronizes, and each thread then reuses each loaded value 32 times. Global loads drop by the tile width; the bottleneck moves to shared-memory bandwidth (two shared loads per FMA).
3. **2D register blocking.** Each of 256 threads computes an 8x8 block of a 128x128 output tile, keeping 64 accumulators in registers. Per k step a thread loads 8 values of A and 8 of B from shared memory and does 64 FMAs: shared loads per FMA fall from 2 to 1/4. This is the step that makes a matmul compute-bound.
4. **Vectorized loads.** Global loads and stores become 128-bit `float4` accesses (fewer instructions, full-width transactions), and A is stored transposed in shared memory so a thread's 8 A values are two contiguous `float4` reads instead of 8 strided ones. `float4` needs 16-byte alignment, so this path runs when K and N are multiples of 4; otherwise the kernel falls back to scalar loads (a grid-uniform branch, so warps never diverge).
5. **Tensor cores (TF32).** The WMMA API issues 16x16x8 matrix-multiply-accumulate instructions on tensor cores. Inputs are rounded to TF32 (10-bit mantissa) with fp32 accumulation, the same contract as cuBLAS with `allow_tf32=True`, which is the baseline it is compared with. Four warps compute a 64x64 tile, each warp a 32x32 piece as 2x2 fragments.

cuBLAS is called through `torch.matmul` with `torch.backends.cuda.matmul.allow_tf32` set explicitly: off for the FP32 baseline, on for the TF32 one.

### Softmax ([`csrc/softmax.cu`](csrc/softmax.cu))

Softmax does about 5 FLOPs per element on 8 bytes (read x, write y), so it is memory-bound: the target is DRAM bandwidth, and the reported metric is effective GB/s for one read plus one write.

0. **Thread per row.** Three passes (max, sum of exponentials, normalize) by one thread. Loads are uncoalesced and only `rows` threads exist.
1. **Block per row.** 256 threads stride across a row, so loads are coalesced, and max and sum are reduced with `__shfl_xor_sync` inside each warp, then across warps through shared memory. Still three passes over the row.
2. **Online softmax** ([Milakov and Gimelshein, 2018](https://arxiv.org/abs/1805.02867)). Each thread keeps a running max m and a running sum d of exp(x - m); when m grows, d is rescaled by exp(m_old - m_new), and two partial (m, d) pairs merge the same way, which is what the warp shuffles reduce. Max and sum come from one read, so the kernel makes 2 reads and 1 write instead of 3 and 1. The same trick is what lets FlashAttention fuse softmax into attention.

All stages subtract the max before exponentiating (no overflow at logits of 1e4), treat -inf as probability 0, and return NaN for an all -inf row, matching PyTorch.

### Fused attention ([`gkl/attention.py`](gkl/attention.py))

Naive attention computes S = Q K^T, writes the N x N matrix to memory, softmaxes it, and multiplies by V: memory traffic grows with N^2. The fused kernel never stores S. Each Triton program owns 64 query rows, streams K and V through in 64-row blocks, and for each block:

1. computes scores with a tensor-core `tl.dot`, scaled into log2 space so it can use the native `exp2`,
2. updates the running row max m and running sum l with the online-softmax rule above,
3. rescales the output accumulator by exp2(m_old - m_new) and adds P V.

At the end it divides by l once. Causal masking skips key blocks entirely above the diagonal, which is why the causal case does about half the work. Off the GPU, the same kernel runs in Triton's CPU interpreter, so CI tests it without a GPU.

### Roofline

A kernel with arithmetic intensity I (FLOPs per byte of DRAM traffic) cannot exceed min(peak FLOP/s, I x bandwidth). The chart uses:

- **Bandwidth:** measured with a grid-stride `float4` copy of 256 MiB ([`csrc/util.cu`](csrc/util.cu)), which is what software can actually reach, rather than the datasheet number.
- **FP32 peak:** SMs x FP32 lanes per SM x 2 (an FMA counts as 2 FLOPs) x peak clock, read from the device. TF32 tensor-core points can exceed this line; that is the point of tensor cores.
- **Intensity:** compulsory traffic only (each input read once, output written once), so a point's x position is the best case for its shape and its height is what it achieved.
